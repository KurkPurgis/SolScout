# Decisions log

Every time something was unclear I made the most reasonable choice and wrote it here (one line of reasoning each).

| # | Decision | Why |
|---|----------|-----|
| 1 | The game project came as `Escape9to5.zip` (uploaded); the only repo I can push to is `SolScout`, so `world_overhaul/` lives at the root of the SolScout repo on branch `claude/rags-to-riches-visual-overhaul-dey2rr`. | It is the only place I may write and push; the game files themselves stay untouched (I only read them from an unzipped copy outside the repo). |
| 2 | There is no `world/` folder and no place file in the zip. The `.rbxlx` is git-ignored and Rojo builds it; its Workspace only holds a Baseplate. The whole world is built by Luau code at runtime (`src/server/World/*`, `Lobby.luau`). So I ran that code to get the world (see #3). | The code IS the world: running it gives the exact parts players see, which is more faithful than any hand copy. |
| 3 | I built a tiny Luau runner (Rust + mlua with the official Luau VM) and a mock of the Roblox API (Instance, Vector3, CFrame, Color3, Enum, Model pivots/scaling, CollectionService...). The unchanged game scripts run on it and every created Part is dumped to `data/world_parts.json`. | Exact positions/sizes/colors straight from the real code, with no manual transcription errors. |
| 4 | Blender was NOT running and no Blender MCP server was connected in this cloud session; download.blender.org and GitHub are blocked by the network policy. I installed Blender 5.0.1 as a Python module (`bpy` from PyPI) and drove it with scripts in background mode. | The goal needs Blender; this is the same Blender, just without a window. All scripts are in `tools/` so you can re-run them in your own Blender. |
| 5 | Renders use Cycles on the CPU (no GPU here, EEVEE needs one). | EEVEE cannot run headless without a GPU in this container. |
| 6 | `icons.blend` only contains the last two icons that were rendered (shrug, sleepy), so I reuse the icon *code* (`assets/icons_3d/scripts/icon_defs.py` colors, bevel style, palm, wheel, chest...) rather than objects from the .blend. | The .blend is overwritten on each render run; the scripts are the real source of the icon models. |
| 7 | Objects are grouped by the builder call and source line that created each part (recorded while the game code runs), then split into touching clusters. Templates = objects with the same shape and colors (with a 0.06 stud tolerance; mirrored copies count as the same). Result: 576 object instances, 125 templates, 0 unassigned visible parts. | Most parts are named just "Part", so names alone cannot tell a bench from a wall; the code that made them can. |
| 8 | Besides the real world (lobby + 4 cities + their auction/podium rooms), I also built a "snapshot" of city 1 in mid-game (8 workplaces, one per job, with kids, debts, Money Makers, FOR SALE and dreams) and a separate "Catalog" area with things that only appear later (Fast Track workplace, every Money Maker/investment, every debt at small and big size, all dreams at full size). The Catalog is never shown in world renders. | Most of what players look at (workplaces, Money Makers, debts, dreams) only exists while a game runs; without the snapshot the inventory would miss the most important objects. |
| 9 | Invisible parts (barriers, label anchors, the FOR SALE buy button) are listed but not remodelled. | They are never seen; they keep doing their job (collision, prompts, labels). |
| 10 | Cities 2-4 and their auction/podium rooms are exact copies of city 1, so each object there is one more *instance* of the same template, not new work. | Same code, same parts, different X offset (700 studs apart). |
| 11 | Objects the game resizes (debts grow with the amount, dreams float at a smaller size in the collection room, the 0.4x mini copies, the see-through FOR SALE copies) get ONE mesh, modelled at the size of the copy in the snapshot. The import plan sets `MeshPart.Size`/Transparency per copy instead of exporting more meshes. | Same shape at a different size is a scale, not a new model; fewer meshes = less to upload and keep in sync. |
| 12 | All words (signs, labels, prices, names) stay on the old parts, which become invisible but keep their SurfaceGui/BillboardGui. The new sign boards sit 0.06 studs behind the old text plane. | Text is set by scripts at runtime (prices, names); baking it into meshes would break that. |
| 13 | Wall boards (blackboard, monitors, office screen, tool board) were 0.2-0.4 studs thick. With the 0.3 minimum part thickness their details may stand up to 0.3 studs further out from the wall (bbox tolerance 0.3 for these four only). Same idea for the 0.1-thick lobby carpet: the extra thickness goes 0.2 down into the floor, where nobody sees it. | Nobody can walk behind or through a wall board, so gameplay is unchanged; paper-thin parts would flicker on phones. |
| 14 | The School Loan debt has 2-7 books depending on the amount, so it gets one FBX per book count (`Debt_SchoolLoan_books2..7`, plus the 3-book template). | A taller stack is a different shape, not a scaled one. |
| 15 | `Dream_Chains` (chains wrapped around a locked dream) is built by code with a varying number of links. I modelled the template as one mesh (6,916 triangles) AND exported the two kit pieces (`ChainSegment` = 2 links, 3 studs; `Padlock`); the chunky links stand up to 0.5 studs outside the thin original bars (bbox tolerance 0.5 for this model only; the old bars stay for any collision). Which one to use is question 2 in REPORT.md. | Whether to swap every link (more parts, exact for every dream size) or one mesh per dream (simpler) is your call. |
| 16 | Very large structures get their own triangle budget: Plaza fountain, plaza disc and city wall 6,000; theme park 3,000; beach villa / private island 6,000; chains 8,000. | They are 10-70x bigger than a prop; still far below Roblox's 20,000 per mesh. |
| 17 | Glow meshes may use any palette color (oven fire ORANGE, police lights RED/BLUE, monitor GREEN). A transparency other than the game's 0.35 is written into the mesh name (`_Glow_GOLD_T55`, `_T100` = hidden until a script shows it). | The original game uses Neon in those colors; the name carries the setting so the import is mechanical. |
| 18 | Small details that would have made an object taller or deeper than the original were moved or flattened (teacher's apple became a badge on the desk front, the graduation-cap button is flat, the hospital-bed cross moved onto the blanket, the toy wheel caps stand out at most 0.13). | The "same bounding box" rule wins over a detail; every object still has its 1-2 details. |
| 19 | Overlapping boxes of the same color on the same plane (red crosses) are now built from non-overlapping pieces (`parts.plus_sign`). | Coplanar overlaps z-fight and render as black specks (seen in the first cabinet render). |
| 20 | Every model is checked automatically for z-fighting (two boxes with faces on the same plane that overlap, ignoring the curved bevel strips; same color too, because it still renders black specks and can flicker; also the flat caps of upright cylinders, and the undersides of the floating dreams, which players see from below) and for parts thinner than 0.3 studs (`tools/blender/check_models.py`, also run by `make_models.py`). All 122 models pass. | Z-fighting showed up as black specks/flicker in several first renders; a check catches every case, not only the ones I happen to see. |
| 21 | The closed auction room is rendered with a soft ceiling fill light, in BOTH the before and the after picture. | The game lights closed rooms with `Lighting.Ambient` (0.16, 0.16, 0.18), which Blender does not have; without the fill both pictures were almost black. Same light on both sides keeps the comparison fair. |
